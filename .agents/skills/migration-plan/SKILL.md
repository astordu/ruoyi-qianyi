# 全项目迁移规划

完整保留原项目功能与界面，随后每轮迁一组可验证的完整能力。源码覆盖清单可以细，执行分组按本 skill 的「分组边界」聚合，不能把每个内容项变成一轮。普通转换由 agent 自行选择；沿用已有用户决定和目标架构。只有行为无法查明、证据冲突或确需改变业务时才询问，不默认开启范围访谈。先读 [状态协议与命令](references/state-protocol.md)。

## 固定清单

1. 查明项目根目录、Vue 源目录、React 目标目录和技术栈。本项目默认候选为 `ruoyi-fastapi-frontend/` → `react-front/`，必须核实符合本次需求。后端仅作契约依据；源码引用其他本地目录时加入源根目录，不把历史报告或目标代码算成待转译前端。
2. 从项目根运行 `python3 .agents/skills/migration-plan/scripts/migration_state.py inventory --root . --source ruoyi-fastapi-frontend --target react-front --state migration/state`，替换已查明路径；额外源根重复传 `--source`。根目录相对状态目录保存，其余路径相对项目根，不填写本机绝对路径。脚本不使用 Git 忽略规则，包含隐藏文件；输出数量、内容哈希和排除记录。复核默认排除目录确属依赖/产物，必要时用 `--exclude-dirs` 替换。
3. 清单不能由模型手写、删行或只列 import 可达文件。未调用文件、测试、配置、样式、资源也登记处理。目录符号链接不被悄悄遍历：核实目标，显式把需迁移的目标目录加入源根；外部依赖写明依据。报告不复制密码、Token 或环境变量值。

## 内容与分组

逐文件阅读，结果写到生成的 `plan.json`，保留稳定编号和已有进度。可分批完成规划，未审完清单不能启动实施。

- 每文件标记 `reviewed`、哈希和 `review_evidence`，登记其中全部待处理内容：导出函数、组件逻辑、模板/条件/事件、样式、注册、副作用、资源和配置。不能只看文件名或文件开头；资源、锁文件等按用途登记，不要求文本逐行转译。
- 每项记录源文件、定位、旧行为依据、目标去向和 `migrate/reuse/exclude`。一个文件可拆多项，一项可有多个目标。复用必须检查框架依赖和兼容性；排除仅用于可证明不需迁移的内容或用户已排除范围，写具体原因，不能凭“未被引用”删除业务功能。
- 先识别页面、公共能力和业务交互，再按下文分组；将逐项映射挂到这些组。不得从文件列表或 AST 函数列表直接生成执行组。工程基础允许无源内容。
- 从 import/export、别名、动态 import、glob、路由/菜单、全局注册、插件和运行入口建立 `depends_on`。组内函数调用和共享状态作为内部关系，不升级成组间依赖。循环涉及同一能力时优先合组；只有两个独立能力之间的循环才考虑接口拆分，不能为解除函数循环创造状态组、逐函数组和最终装配组。
- 每组写 `groups/Gxxx/contract.md`：可观察交付、本轮边界与拆分依据、全部源内容、目标映射、依赖、正常/异常/边界行为、原版证据、验证方式、待页面集成项。条件来自旧代码或运行结果；函数名、源码哈希和分支数量只能作定位，不能代替具体输入输出和操作场景。
- `entry_priority`：工程基础 0，登录/导航等主入口 1，其他业务/资源 2；不能绕过依赖。`feature` 为功能名，公共组可用 `shared`。
- 列出 `integration_checks`，覆盖接入页面和跨页面流程。公共函数/组件可本组验证后供其他组使用，不等整个页面；项目完成必须补集成与相关回归。

## 分组边界

本项目执行组采用以下默认范围；这是单轮交付范围，不缩减全项目迁移范围。

| 内容 | 默认一组的交付范围 |
| --- | --- |
| 工程与构建 | 工程可启动、配置生效、构建可用；同类环境配置、配套启动脚本一起处理 |
| 普通业务页面 | 一个页面的完整交互，含查询/分页、增删改等该页面实际存在的行为、API 接入、权限、加载/错误和样式；通常一组完成 |
| 复杂页面 | 按业务闭环拆成 2–5 组，如列表筛选与分页、编辑与提交、一个完整配置弹窗；每组完成对应事件、状态、请求、失败恢复和页面接线 |
| 公共工具或协议 | 一个完整能力及所需状态、辅助函数和导出，例如时区偏好解析、日期解析与格式化、时间字段序列化；确有独立协议边界时再拆 |
| 公共组件 | 一个组件的完整 props、交互、状态、样式与导出；内部简单子组件和事件处理函数随组件一起迁移 |
| 复用资源与同类配置 | 同一用途资源批量复制/适配并验证引用、内容和加载，例如 SVG 图标批次、多环境压缩配置；每文件仍保留独立内容映射 |

- 单个 getter/setter、普通辅助函数、AST 语句、模板节点、CSS 选择器、图片或配置键不得各自占一个执行组。只有源码证明它是可独立复用与验证的完整能力时，才允许小组单独存在，并写明依据。
- 同一能力的共享状态、协作函数、生命周期和必要导出/页面接线默认同组。不把「状态壳 → 几十个函数 → 最终装配」作为拆分模板；完成后应可使用该能力，而非等待另一组补齐内部接线。
- 一个页面/组件作为主要交付对象时，通常 1 组，复杂情况 2–5 组。超过 5 组先做合并复核；仍需超过时逐组说明独立业务结果、不同依赖/验证边界及不能合并的原因。它引用的已存在公共组不重复计入页面组数。不靠缩减测试或遗漏功能满足数量范围。
- 文件长、函数多、内容项多或一次会话做不完不能单独作为拆分依据。大文件可在一个能力组内分步骤实施并续跑，步骤不生成新执行组；独立业务闭环仍可拆开。无关页面或公共能力也不能为了减少数量合在一起。
- 为每组登记 `outcome`（完成后能观察/使用什么）、`scope`（完整闭环及交由其他组的边界）；同一能力拆多组时填写 `split_reason`。组标题使用能力名称，不默认使用「文件名：函数名」。

规划交付前复核所有单内容项组、同一源文件关联多组和页面/组件超过 5 组的情况，合并同用途资源/配置及共享状态下的协作函数。给出文件数、内容项数、执行组数、各页面/组件主要交付组数和保留拆分的理由。总组数由复核后的能力边界决定，不预设几百组或按文件数/函数数估算。脚本检查登记完整性，不能代替本轮分组复核。

已有历史 PRD、进度与基线只作参考，重读源码并核对版本后才能使用，不自动标通过。技术方案沿用已定目标架构，核实源状态、生命周期、表单、路由、权限、请求和样式的真实语义。

运行 `migration_state.py check --state migration/state`。文件审阅、内容映射、依赖和合同完整且快照一致，才能交给 [migration-next-group](../migration-next-group/SKILL.md)。脚本证明登记完整性，不证明模型理解全部代码。规划阶段不改 Vue/后端、不实现业务。
