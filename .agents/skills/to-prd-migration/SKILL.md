直接综合已确认的访谈摘要和代码理解，不再重复范围访谈。PRD 保存到当前项目的 `.qoder/prd/<module-id>.md`，作为后续实施与验证的统一需求入口。

从模块入口沿事件处理、API、组件、状态和权限读代码；必要时查后端契约。用“入口 → 动作 → 分支 → 可观察结果”还原场景，每个发现映射到场景或明确排除。查到与已确认范围冲突或影响验收的未知项，列成待确认问题；先完成有依据的草稿，不自行扩大范围。

读 [Vue → React 技术约定](../../../migration/vue-react-convert.md) 中与本模块相关的部分，记录共享依赖和真实接口。源码路径作为独立证据区保留，方便后续 agent 重读；不能只列读过的文件而没有对应行为。

## PRD 内容

1. **问题与目标**：迁移哪个模块，用户目的，明确的源/目标目录（相对项目根目录或绝对路径），实际技术栈及已定目标方案。
2. **范围与确认**：入口、纳入/排除项、访谈中的真实反馈；PRD 自身标为待确认或记录实际确认。
3. **用户场景**：稳定 S001 等编号，角色/权限、前置数据、步骤、结果、成功/失败/校验/取消/空数据/分页/刷新等相关分支。
4. **验收条件**：稳定 C001 等编号，关联场景，写清可观察结果、请求与副作用及验证办法。不得只写“功能一致”或“页面正常”。
5. **源码证据**：稳定 E001 等编号，项目相对路径、实际函数或模板绑定、读取时的行号、支持的行为；每条验收条件引用对应证据。附调查日期，有 Git 时记 revision。
6. **实现决策与依赖**：已确定的路由/接口/共享能力；区分原版行为、已知旧缺陷、用户要求的改善和未定技术选择。
7. **测试与截图计划**：每条条件如何检验、数据与账号要求、旧版截图状态、目标对比状态。现成测试是否可运行必须核实；函数单测、UI 操作、请求检查、截图各自承担适当条件。
8. **实施清单与待决项**：按可独立验证的行为列短任务和依赖。小模块一个任务即可；无需另建任务 JSON 或工单系统。

条件示例：“取消编辑不发送更新请求”“无权限角色看不到按钮，直接路由访问按原守卫规则处理”“保存后刷新列表并保留已确认的查询状态”。举例不能代替从本模块读取的真实行为。
